# CI Manager

A personal project & task management system that runs on your own PC.

It needs nothing except **Node.js**. The data is kept in a single **SQLite** database file using the SQLite engine built into Node, so there is no database server to install or run. You can open that file in **DBeaver** to browse, query or edit the data.

**Your data lives outside the app folder**, in `%LOCALAPPDATA%\CIManager` (i.e. `C:\Users\<you>\AppData\Local\CIManager`), which holds `taskmgr.db`, `backups\` and `logs\`. Updating, re-cloning or deleting the app folder never touches it. The **Backups** page in the app shows the exact path.

## 1. One-time setup (Windows)

### The quick way: `CIManager-Setup.bat`
With Node.js 22.13+ and Git installed, put **`CIManager-Setup.bat`** (from this repository) in the folder you want the CI Manager in, e.g. `C:\CIManager`, and double-click it. It checks Node.js and Git, downloads the code into an **`app`** folder next to it, installs the dependencies, makes a **CI Manager** shortcut with the CI Manager icon (a `.bat` file can't have an icon of its own, so the shortcut makes it look and start like an application; the first install also puts it on the desktop), writes **`READ ME - where things are`** in two versions, a `.txt` for Notepad and a `.md` for Obsidian (front matter, tables, callouts and links that open each folder), with the folder layout, where your data and backups are, the shared paths and the optional settings, all with that computer's actual paths, then starts the app.

**Sharing it on the network:** put `CIManager-Setup.bat` in a network folder and tell people to double-click it there. To give it an icon there too, make a shortcut to it in the same folder (right-click › *Show more options* › *Create shortcut*), rename it e.g. *Install CI Manager*, and under *Properties › Change Icon…* pick `cimanager.ico` from the repository's `assets` folder (copy the icon to the share first). Run from a network folder (a `\\server\share` path or a mapped drive) it installs on their own computer, in `%USERPROFILE%\CIManager`, and puts a **CI Manager** shortcut on their desktop; the copy on the network is never changed.

**The same network paths for everyone:** on **KPIs › Sources › 🌐 Shared paths**, click **⬇ Export these paths for everyone** and save the file as **`cimanager-defaults.json`** next to `CIManager-Setup.bat` on the share. Each install made from there points at that file (`DEFAULTS_FILE` in `app\.env`, as a `\\server\share` path even when it was run from a mapped drive) and reads it every time the app starts. It holds the CI workbook, the A3 folder and file name, the KPI source files and forecasts, and Planning's export paths (the work orders, Matching and card database exports and the shared planner address). A path is filled in only where it's blank, still the built-in default, or still what the file said last time, so a path someone set for themselves is kept and a path changed in the file reaches everyone else at their next start. Off the network the app just carries on with the paths it has. **📂 Use a paths file…** fills them in from a file by hand, and **🔄 Read the shared file now** applies an updated file without restarting.

**Start at log-in:** on the first install the setup asks *Start the CI Manager automatically when you log in to Windows? [Y,N]*. Yes puts a **CI Manager** shortcut in the Windows Startup folder (`shell:startup`), so it starts, and updates when there's a newer version, each time you log in; updates keep that shortcut up to date. To change your mind later, press Win+R, type `shell:startup`, and delete the shortcut there or copy the CI Manager shortcut in. No Task Scheduler task or admin rights needed.

**On the taskbar:** right-click the **CI Manager** shortcut › *Pin to taskbar* (Windows 11: *Show more options* first). The shortcut runs the launcher through `wscript.exe`, which is what makes Windows offer pinning. The app can also be **installed from the browser** as a window of its own: with it open in Edge or Chrome, use the browser's **⋯ › Apps › Install CI Manager** (or the install icon in the address bar). It then opens without the browser's tabs and address bar, with the CI Manager icon in the taskbar, and can be pinned there too. The installed app only shows the page, so the CI Manager must be running (the shortcut or start-up at log-in takes care of that).

**Updating is automatic:** each time the **CI Manager** shortcut starts the app, it first checks GitHub for a newer version (a quick `git fetch`; offline, it just starts). If there is one, it runs `CIManager-Setup.bat` in a window: stop, back up your data, pull the latest version, reinstall the dependencies, refresh the shortcut and the read-mes, and start the app. If the app is already running, the shortcut just opens it; the update comes at the next start. Stopping is done in the app (**⋯ › Stop server**), so the one shortcut is all anyone needs. To update straight away, stop the app and double-click `CIManager-Setup.bat`; to turn the automatic check off, put `AUTO_UPDATE=0` in `app\.env`.  Your data stays in `%LOCALAPPDATA%\CIManager`, outside the folder, so installing or updating never touches it. Run from inside an existing clone of the repository, it updates that clone in place, the same as `update.bat`.

The steps below do the same by hand.

**Prerequisite:** Node.js **22.13 or newer**. Check your version with `node -v`. If yours is older, install the current LTS from <https://nodejs.org> (the Windows installer doesn't need admin rights if you choose *Install for me only*). No database server is needed.

1. **Get the code** into a folder, e.g. `C:\TaskManager`.
2. **Install and start:** double-click **`start-hidden.vbs`**. It installs dependencies the first time (you'll see a window for that), then starts the app in the background with **no console window** and opens <http://localhost:3000>. Double-clicking it again while the app is running just opens the browser.
   - **To stop it:** click **⏻ Stop server** in the top bar's **⋯** menu, or double-click **`stop-server.vbs`**.
   - **`start.bat`** does the same but keeps a console window open that shows the log. Use it if something isn't working. Closing that window stops the app.
   - Or, from a terminal in the folder (in VS Code: *Terminal → New Terminal*):
   ```
   npm install
   npm start
   ```
   The database is created automatically on first start in `%LOCALAPPDATA%\CIManager`. If you used a version from before the rename to CI Manager, the old `%LOCALAPPDATA%\TaskManager` folder is renamed to `CIManager` automatically on the first start (if something has a file in it open, e.g. DBeaver, the old folder keeps being used and a warning is logged; close it and restart). If you used an earlier version that kept `data\taskmgr.db` inside the app folder, it's moved across automatically on first start (the old file is renamed to `taskmgr.db.migrated`), and old backups are copied too.
3. **Enable desktop alerts:** click **🔔 Enable desktop alerts** in the top bar's **⋯** menu and allow notifications. Reminders only fire while the app is open in a browser tab, so keep it pinned in Edge or Chrome.
4. *(Optional)* To change the port, database location or backup settings, copy `.env.example` to `.env` and edit it.

### Start automatically when you log in (optional)
Press `Win+R`, type `shell:startup`, and put a shortcut to **`start-hidden.vbs`** in the folder that opens (right-click the file → *Show more options* → *Create shortcut*, then move the shortcut). The app then starts silently at log-in and opens in your browser.

> If Windows reports that VBScript isn't available (Microsoft is gradually retiring it; it's still installed by default on Windows 10 and 11), use `start.bat` instead.

### Getting updates (during development)
`start-hidden.vbs` (what the **CI Manager** shortcut runs) checks for updates when it starts the app, as above, if `CIManager-Setup.bat` is next to the app folder or in it. Or update by hand:

Double-click **`update.bat`** in your clone of the repository. It:
1. stops the running CI Manager (whether it was started hidden or with `start.bat`);
2. takes a backup of your data;
3. runs `git pull --ff-only` and lists the new changes;
4. runs `npm install` in case dependencies changed;
5. starts the app again and opens it in the browser.

This needs Git installed and the app running from a `git clone` of the repository. Your data is in `%LOCALAPPDATA%\CIManager`, outside the repository, so pulling never touches it (and `.env` is git-ignored). If the pull fails (for example, because you've edited a tracked file), the script says so and restarts the version you already had.

When an update changes how data is stored, the app upgrades your database automatically on its next start. Before any structural change it saves a copy of the database as `backups\db\pre-upgrade-<date>.db` in your data folder, and it checks every link between records afterwards; if anything doesn't add up, the upgrade is undone and nothing is changed.

## 2. Everyday use

- **New project:** click **+ New** in the sidebar. List the baseline tasks one per line. The baseline is set automatically.
- **Add a note as you go:** type in the bar at the top of the project and press **Enter**. Notes are time-stamped. To attach a note to a specific task, pick the task in the drop-down first.
- **Add a task:** type in the *Add a task…* box and press **Enter**. Shortcuts you can include in the text:
  - `!low` `!high` `!crit` sets the priority
  - `@today` `@tomorrow` `@fri` `@2026-10-31` sets the due date

  For example, `Send board pack !high @thu`.
- **Subtasks:** hover over a task and click **＋ sub**, or open the task and use *Add subtask*.
- **Task details:** click a task title to edit its description, status, priority and due date (changes save automatically), and to add subtasks, reminders and notes or see its history.
- **Boards:** **🗂 Board** in the top bar shows all ongoing projects; drag a card between *Active*, *On hold* and *Completed*, or click it to open the project. On a project page, switch the Tasks panel between **☰ List** (tick-box checklist with subtasks) and **▦ Board** (that project's own Kanban: drag tasks between columns). The choice is remembered.
- **Due-date alerts:** a pop-up appears once on the day a task is due, and again once it becomes overdue.
- **Re-baseline:** use this after an agreed change of scope. All current tasks become the new baseline.
- **Keyboard:** `N` quick note, `T` add task (in a project), `/` search, `[` hide or show the sidebar.
- **Layout:** the page tabs (Dashboard, Tasks, Calendar, Board, Ideas, Library, Report, Contacts) and search are in the top bar; Activity log, Backups, Settings, dark mode, desktop alerts and Stop server are in its **⋯** menu. The sidebar is kept for your projects list; **☰** at the left of the top bar (or `[`) hides it for more room and brings it back, and the choice is remembered. On a smaller window the tabs show icons only (hover for the name).
- **Closing windows:** click anywhere outside a pop-up window (or press Esc). Windows that save as you go (tasks, meetings) save first; a form you haven't saved yet (new project, phase, person…) asks before discarding what you typed. Clicking outside the 📇 contacts book keeps what you ticked.
- **Repeating tasks:** add `*weekly` (or `*daily`, `*weekdays`, `*fortnightly`, `*monthly`, `*quarterly`, `*yearly`) when adding a task, or set *Repeats* in the task window.
- **Waiting on someone:** fill in *Waiting on* in the task window (names you've used are suggested). Clear it when they've replied.

### ⏱ Timing (Production › 🧠 Insights › ⏱ Timing)
What really ran, from the daily **timing reports**: perso's *DailyPersoTiming* (one row per job run: the machine, start and end date and time, cards persoed, remake, customer, item), and Matching's matching report.
- **Link the report** where it's saved (on the Production tab, or ⚙ there). It's read every 10 minutes and **every run is kept**, so the history builds up day by day even though the report only holds one day; reading a report again updates its runs rather than adding them twice. **📂 Load reports…** takes older daily reports (several at once) to fill in the past. The columns are found by their names, in any order. **The history starts when the report is linked**: the daily report only ever holds one day, so to see earlier weeks or months, export the timing report once for a longer period (e.g. the last 3 months, same columns) and load it with 📂 Load reports… (3 months of runs load in about a second). The page opens on the latest day with runs.
- **Every run the report holds is kept, whatever its day**: a report covering several days or months fills in all of them. A **history strip** at the top shows every day kept (cards a day; click a day to open it), and the report line says what the report itself held when last read (e.g. *the report held 8,090 runs over 66 days*). Views: a day, 3 days, a week, two weeks or a month.
- **Work orders starting with M** aren't taken in at all: they're skipped when a report is read or loaded (and any kept by an earlier version are removed).
- **Efficiency** for each run (last column of ☰ Runs, also in the anomaly list and when a bar is clicked): what a job that size usually takes on that machine (its set-up plus cards × its time a card) ÷ what it took. 100% is a usual run, more is quicker, less is slower; green from 90%, amber from 70%, red below. Per machine and overall in ▦ Load, and overall in the tiles.
- **Customers** come from the work order, as in Planning: characters 2–4 of the job (*CADXS2610…* → ADX), else the report's CO Ref; the full name comes from Planning's card database when the report has none.
- **▤ Gantt**: a row per machine and a bar per run, coloured by customer (striped: remake). Gaps are a machine standing still; shading is outside the working day from Planning's Setup. Click a bar for the job, its times and what the machine usually takes for a job that size. One day, 3 days, a week or two weeks, with ◀ ▶ to move.
- **▦ Load**: machine time busy per machine per day (runs that overlap on a machine count once), as a share of the working day, with the cards made and each machine's average time a card. **☰ Runs** lists every run.
- **Anomalies are set aside automatically.** Each machine's usual **set-up time** and **time a card** are learned from its own runs over the last 120 days (a robust line fit, which the odd bad run doesn't move), so a run is compared with what a job *that size* should take on *that machine*. A run is an anomaly when it's at least **3× quicker or slower** than that (*Normal*; *Strict* 2×, *Loose* 5×) and well outside the machine's usual spread. Runs over 24 hours, ending before they start, or with nothing made are always set aside, and a run without an end is shown as still open. Anomalies are left out of every figure and listed with the reason (e.g. *28× slower than usual on MX#1 (18.4 h for 928 cards, usually about 40 min)*); **count them anyway** puts them back (dashed on the Gantt).

**⚠ Anomalies to Excel**, for investigations, puts the timing runs that were set aside into one workbook. Open it from ⏱ Timing, the ⚠ Anomalies table, or 🔬 Learned's "anomalies left out". Choose the period (30 days to a year, or any dates) and the strictness; the workbook has:
- **Anomalies by WO:** each work order with runs that can't be right for their machine and size (far too slow or quick, no end time, impossible). Each row shows the runs, kinds, cards, minutes against the usual, the worst run, the machines, the dates and where the work order stands in the export now. Empty **Cause · Action · Owner · Closed** columns are there to fill in.
- **Anomalous runs:** every one of those runs, with how far off it was.
- **Read me:** what's in it and the period.

Card articles missing from the database are listed; a line without a speed gets the flat rate if one is set, else the average of the others (marked ≈).

With machines set, each card line is planned on the running machine able to run its type that comes free first; a type no machine runs is flagged.

(A machine running several types counts for each — the ceiling for that type on its own.)

Jobs are worked through in the list's order — running ones first — and each gets its production time and a **projected finish**, red when it would miss its cut-off; the tiles count the jobs projected late. Click a job for each card's type, material, print sides, speed and time.

- **Estimated OEE by customer** (Setup): each customer (the trigram in the work order) in the open work orders is listed with its cards open and its name from the card database; type an OEE % and its jobs are planned at speed × OEE (1,000 cards/h at 80% → 800/h). It gives two figures: the overdue on its own ÷ output a day, and, with new work still coming, overdue ÷ (output − due), with the working day it's reached. If as much or more is due each day as is done, it says the backlog isn't shrinking. The Overdue tiles now show cards / items, with the catch-up days.
- **🔬 Learned** (🧠 Insights): Planning learns from what really ran, the runs in the ⏱ Production timing reports (🧠 Insights › ⏱ Timing), over the last 30 days to a year, with anomalies left out and each card matched to the card database.
  - **🔬 Card by card (run times learned item by item):** each card line in a work order is timed as the usual set-up plus its cards at that card's own running speed, learned from its runs. A card with few runs leans on its kind of card: one run counts for little, ten for most. The kind's speed is adjusted by how that customer's cards usually run. A card with no history takes its kind's speed. A card with no history whose kind has none either takes all runs' speed, unless a speed rule covers it, in which case the rule is kept. So a work order with several different cards is timed by what's actually in it. Switch it on with **Use it in the plan**, or in ⚙ Setup › **Run times**. Lines timed this way show 🔬 by their speed; hover over it to see how many runs it's based on and the set-up added. Every later step (machines, Gantt, load, mitigation and the projected finish) uses these times. The model uses the last 180 days of runs and updates as new timing reports come in. The Accuracy tiles compare all three ways on the newest runs.

  - **Speeds by kind of card** (type · material · print sides): the running speed once a run is going, with the machine's usual set-up taken off. It's the middle of the runs, weighted by cards, with the range half of them fall in, set against the speed planned now. **Apply** adds or updates that exact speed rule. **Apply the confident speeds** does all the rows with enough runs: ●●● 30+ runs over 5+ days, ●●○ 10+ over 2+ days. ●○○ rows are left for you to judge.

### 📐 Capacity planning (CPM)
The macro view for **Prod Management** (📐 Capacity in the menu; part of the Production module). It weighs the year's forecast against what the machines can do, month by month or week by week, per technology (DOD / Emboss / Laser).
- **Forecast** comes from the files linked in **Reporting › Sources** (*BeNeLux forecast* and *Amex forecast*), read with the SITHUB rules: BeNeLux = Line_Qty where Man_SubArea_Nm is "Benelux" and Item_Nm contains "basic", per customer and month; Amex = the Sittard sheet's TOTAL BAU row per month, with its LASER / EMBOSS + CRAT / DOD rows as Amex's own split. (SITHUB looks every Amex month up against 01/01/2026 — that isn't copied.) Each new version of a file is kept as a snapshot, so later you can see what was forecast when.
- **Customers** (tab): each customer's trigram, the forecast names that map to it, its split across the technologies and its OEE. Blank split: learned from what ran (the card database's card type per item); blank OEE: Production's OEE for it, else the default. **Import from the CPM workbook** reads its Config sheet. The whole forecast counts even before anything is set up here: a forecast name not linked to a customer takes the mix of everything persoed (or, with nothing to learn from, the machines' capacity) and the default OEE, and the Overview says how much is unlinked — link a name by typing its trigram on Customers.
- **Needed** = forecast × flex × split ÷ OEE. **Capacity** = speed × working days × shifts × productive hours (6 by default — breaks and change-overs out) × availability. Speeds and machines are Production's (⚙ Setup) and follow it as it changes — each technology's own speed rule, else the average of its material / sides rules, else a rule for any type, else the flat rate (the Capacity tab shows which); the **Capacity** tab sets shifts, hours, holidays, the default OEE and, per machine, the share available to perso and any speed of its own. A machine that runs several technologies gives its hours to whichever is short.
- **🕐 Day by hour** (the CPM daily sheet): a working day of the month chosen, hour by hour from the day's start (Production's, 06:00), for the base plan or a scenario. Each customer and technology's month (forecast × split, × flex) ÷ the month's working days is split into **daily** work and **renewals** — renewals being the Low priority work orders, each customer's share learned from the last 4 months (type a % to set it). The daily part is spread over the hours by **when that customer's work orders arrive** — when they first appear in the hourly open-order export, midway between that export and the one before (an order first seen after a gap of more than 2 hours, or Low priority, is left out); else all of the technology's arrivals (the table shows each customer's typical arrival time and how many of its orders were timed; if the export wasn't read at some hours — the app not running overnight — it says so, as those arrivals can't be timed: the shared server avoids it); or, chosen on the tab, as its cards were produced (the ⏱ timing report); else evenly over the hours worked. Each technology's chart has a mini-tab, **As it comes in / Smoothed capacity / Work orders**. **Work orders** runs the day as the floor does: each customer's day cut into work orders of its usual size (the median lately, shown in the customers' table), coming in at its usual times, each run as a block, start to finish, on the first free machine that runs its technology (and may run that customer), first come first served — renewals only in their window — over three days, the middle one shown; a machine Gantt shows the blocks (red: finishing after the cut-off), the chart what's on the machines each hour and what's waiting, and the late work orders are listed. **Smoothed capacity**: the daily work is done in the order it comes in, each piece in the spare capacity of its hour, then the next hour with spare capacity and so on, around the renewals — with the day as it came in drawn dashed, the peak load and hours over before and after, and what's done after its shipping cut-off (its commonest one lately, else the commonest of all, or typed for it in the customers' table; after the cut-off, the next day's). **🚚 Shipment times** sets the cut-offs drawn on the charts — add, remove, change and label them (e.g. 17:00 PostNL), saved together — or goes back to the ones learned from the work orders. **Capacity needed** (the default, as the CPM daily sheet) shows them ÷ OEE against capacity at speed; **Cards** shows the cards themselves against the capacity × the hour's OEE, with dots for what was **really persoed** on an average working day (the month's runs, else the last 4 weeks) and a *real vs model* row; renewals ÷ (OEE + 5 points, settable) go evenly over each technology's **renewal window** (hours ticked on the tab, or set by a scenario's 🔁 change). Capacity in an hour is each machine's speed × availability in the hours the shifts cover — full speed, or the productive share (6 of 8 h) — a machine running several technologies split as it ran in that hour. Each technology's tile sums its day up: the month's forecast ÷ working days = cards a day → capacity needed. Each hours table ends with the day (summed; the load and the real vs model difference for the day; what's left at its end), and the customers' table with a total per technology and for all of them (of every line, not only those shown). Charts per technology (daily + renewals against capacity, what's carried over to the next hour, the shipping cut-offs), the load of all three, the hours table, and a heat map of where each customer's day lands. **⬇ Excel** saves it like the CPM daily sheet: a row per customer and technology with formulas over the renewal %, volume, OEE, hour profile (its own sheet), renewal windows, hours worked, speeds and shares, with charts.
- **Forecast vs actual (flex)**: upload previous years' workbooks (forecast and actual per customer and month); with the months since the snapshots began, each customer's flex (actual ÷ forecast) is worked out per month and year. **Apply flex** on the Overview scales the forecast by it.
- **All technologies** (Overview, top): the three together in their CPM-workbook colours (DOD teal, Laser purple, Emboss dark) — *Cards*: capacity needed as bars with a tick at each one's capacity (red where it's short); *Load %*: each one's load as a line against 100%. The colours carry through the tiles, headings, the forecast vs actual picker and the Excel export (charts, and each row's text as the CPM workbook colours it).
- **Capacity per machine** (tick box on the Overview and on 🕐 Day by hour): each technology's capacity line split into each machine's part, stacked — a coloured band per machine (its hours on the technology × its speed; by the hour on the day, a restricted machine only what it may run), each machine the same colour everywhere.
- **Overview**: per technology, bars of the capacity needed (green, amber from 85%, red over), the forecast inside and the capacity line, with a legend, data labels (by month) and the table below; the volume axis runs in even steps (0.1M for small figures, else 0.25M or 0.5M). **📈 Forecast vs actual** sets the cards forecast beside the cards persoed (DailyPersoData, else the timing report) per month or week — all technologies or one — with the difference on each, this month so far shown lighter, and the totals to date. **By week** uses ISO weeks, spreading each month over its working days.
- **⬇ Excel** (Overview) saves what's on screen — the year, by month or week, flex on or off, and the scenarios compared — as a workbook laid out like the CPM one: a sheet per plan (the base and each scenario) with the working time, the forecast per customer and technology (split and OEE beside it), the forecast by technology, the capacity needed, each machine's hours and capacity, and a summary per technology (capacity, needed, open, load coloured, forecast, actual, actual vs forecast). The figures are formulas over the inputs (blue on yellow: split, OEE, availability, speed, working days, shifts, hours), so they can be changed in Excel and the rest follows; a figure a scenario fixes for one period is grey. Then native Excel charts, the forecast check against SITHUB and each scenario's changes.
- **Scenarios**: your own list of changes — speed, add / remove a machine, what a machine runs, shifts and hours, OEE, a customer's volume, a new customer — each from a month (and until one). Scenarios are yours; tick **share** to let the rest of Prod Management see one (they can copy it, not change it). Compare up to two on the Overview: each technology chart marks the scenario's capacity needed across the bars and draws its capacity dashed, and the table gives its needed, capacity and load. A change that would do nothing, or only shows elsewhere, says so on the Overview and in the editor: a machine added running nothing or set to run nothing, a machine that isn't there, a change that ends before it starts, a 0 change, a machine kept for customers with no forecast, a new customer's split not adding up to 100% (taken as shares of it), and the renewal window (🕐 Day by hour only). An OEE change lowers the capacity needed, not the capacity; a restriction lowers capacity only by the hours it leaves idle. **🔒 Restrict a machine** lets a machine run only some customers and/or some cards — any card database column (material, cardbody name, print sides, tag, provider, type) and the values ticked. Each customer's volume is split over those values as it was persoed in the last year; work goes to the machines allowed it (the restricted ones first), and work no machine may run shows as *can't be placed* (and the period as over). A restricted machine's capacity is only the work it's given: the hours it has left are idle — no one else may use them — so they come off the scenario's capacity and show as *idle on restricted machines*.

## 1a. One shared copy on a server (everyone on the network)

Instead of a copy on each PC, one computer runs the CI Manager and everyone opens it in the browser. Everyone then shares one database, one setup and one history.

**Setting up the server** (an always-on Windows PC or VM with Node.js and Git):
1. Run `CIManager-Setup.bat` on the server as usual. Run it from the server's own disk, not from the share, so it installs there.
2. In the app folder, right-click **`server-install.bat`** › *Run as administrator*. It asks for:
   - **port** and **data folder**: keep the data folder on the server's own disk (default `%ProgramData%\CIManager`);
   - **whether to start from the database already on that PC**, if there is one, for example yours. The database is copied and the original is kept;
   - **the Windows account to run it as**: it needs to read the network folders the app reads (the KPI workbook and sources, planning exports, card database and timing reports) and write to the A3 folder. In the app, use `\\server\share\…` paths, because the account has no mapped drives;
   - **the address people will open**, e.g. `http://cimanager:3000`.

   It then sets `HOST=0.0.0.0`, `PORT` and `DATA_DIR` in `.env`, opens the port in Windows Firewall (domain and private networks only) and makes a scheduled task, **CI Manager server**. That task runs `server-run.bat` at start-up, whether anyone is logged on or not, and starts it straight away.
3. Copy the two files from the app's **`for-the-share`** folder (`cimanager-server.json` and `cimanager.ico`) next to `CIManager-Setup.bat` on the share.

**Everyone else:** they double-click `CIManager-Setup.bat` on the share as before. With `cimanager-server.json` there, it installs nothing. It puts a **CI Manager** shortcut on the desktop that opens the server, in its own window in Edge. It also stops their own copy from starting at log-in. That copy's data stays in `%LOCALAPPDATA%\CIManager`, and they can stop it from its ⋯ menu.

**Keeping it running and up to date:** `server-run.bat` starts the app again 15 s after it stops unexpectedly. It updates the app before starting it, backing up the data first. Each night at `UPDATE_HOUR` (default 3), the app checks for a newer version and, if nobody has it open, restarts to install it. `AUTO_UPDATE=0` in `.env` turns updates off. Starts, stops and updates are written to `logs\server-run.log` in the app folder; the app's own logs are in the data folder.

**Working together:**
- **Names:** each browser is asked for a name once; change it in ⋯ › *Your name*. It shows others who's here, and it's saved with every change in the activity log and history.
- **👥 in the top bar:** who else has the CI Manager open and where. On a project, an idea, the KPIs or Planning, a line says who else is on the same page.
- **Changes by others:** lists (Dashboard, Tasks, Board, Calendar, Ideas, Contacts) refresh by themselves when someone else changes something, unless you're typing or have a dialog open. Other pages show a yellow note saying who changed what, with **🔄 Refresh**. A task you have open says so inside its dialog.
- **No silent overwrites:** a text box remembers what it said when you started editing. If someone else saved a change to it before you, your save is held, and both versions are shown side by side. Keep theirs, or save yours, after editing it to take in theirs if you like. The version not kept stays in the history. Fields like status, dates and owner just save; the last change counts.
- **🕘 History** (on a project, idea, task or meeting): every change, newest first, with who and when, and each field before and after. **↩ Put back** sets a field back; that is itself a change, so it can be undone too.

**👤 Accounts and 📥 My work.** Accounts are off until someone makes the first one, so until then nothing changes. In ⚙ Settings › 👤 Accounts, make your own account first; it's the admin, and from then on everyone signs in.
- **Adding accounts:** the admin adds one per person, picking the person from the contacts (the name used as task owner, project leader, sponsor or team member). They also give a username and a first password; the person must change it at their first sign-in.
- **Managing accounts:** the admin can set a new password (again changed at the next sign-in), make someone an admin, turn an account off, or remove it. There's always at least one active admin.
- **Signed in:** your name is your account's person, so who's here and who changed what come from it, and you're never asked for a name. The ⋯ menu has 🔑 Change password and ↪ Sign out. A sign-in lasts 30 days from when it was last used. After a few wrong passwords from one PC, it waits a minute.
- **📥 My work** (top left, with a count of what's new) shows:
  - **New for you:** tasks someone else gave you and projects you were made leader, sponsor or a team member of since you last looked, with who and when. **✓ Mark the new ones as seen** clears them.
  - **My tasks:** open tasks with your name among the owners, by due date.
  - **My projects:** active projects where you're the leader, the sponsor or on the team.
- **🧩 Modules:** the admin ticks which parts of the app each account can see and use, in ⚙ Settings › 👤 Accounts (the Modules column, or when adding an account).
  - **Basic pack**, always included: Home, Tasks, Calendar, Library, 📥 My work, quick notes and search.
  - **To tick:**
    - **🗂 Management:** Projects (the board, project pages and charters, the projects list in the sidebar) and 📊 Reporting (the Weekly Ops Report, its database and sources).
    - **💡 Continuous Improvement:** Ideas.
    - **🏭 Prod Management:** Production, including 🧠 Insights and its ⏱ Timing.
    - **🗄 Archive:** the status report.
    - **📇 Admin:** Contacts, for editing the lists. Names can still be picked as owners without it.
  - **Carried over:** ticks made before the grouping move across. Projects or KPIs become Management, Ideas becomes Continuous Improvement, Planning becomes Prod Management, Report becomes Archive and Contacts becomes Admin.
  - **Presets** when adding an account: *Basic pack only*, *Production: Basic + Prod Management* and *Manager: everything*.
  - **What's hidden:** a module an account doesn't have drops out of the top bar, the dashboard and search. Its pages send them to the dashboard, and the server refuses its data to that account.
  - **Who has everything:** admins always have every module. Accounts made before modules existed have them all until an admin changes them.
  - **When it applies:** a change takes effect the next time that person opens or refreshes the page.
- **🔑 The host and admin rights:**
  - **The host:** the first account made, or on an existing install the longest-standing admin. It has everything and can't be turned off, removed or changed by anyone else.
  - **Giving rights:** only the host gives admin rights. In ⚙ Settings › 👤 Accounts, set someone to **Admin** (every right), or leave them a User and tick some of these:
    - **⚙ Change the setup:** Settings, Planning setup and modifiers, applying learned speeds, KPI sources, the library, the team pack.
    - **👤 Manage accounts:** add, turn off and remove accounts, set new passwords, choose modules. Not the host's account, admins' passwords, or anyone's rights.
    - **💾 Backups:** make a backup and **restore one from any PC**, not only on the server.
    - **🖥 Server:** a 🖥 Server card in Settings with the **📜 Server log** (today's, newest first, with a warnings-and-errors filter) and **🔄 Restart (and update)**. Under `server-run.bat` the restart checks for an update, installs it and starts again, and your page reloads when it's back.
  - **What it's for:** your own account can fix and change things from your PC instead of remoting into the host. Rights apply when that person next opens or refreshes the page.
  - **Still only on the server itself:** stopping the server for good, and resetting a forgotten host password (`scripts/reset-password.js`).
- **🔒 Setup is for admins** (or accounts with that right):
  - **What only they can change:**
    - ⚙ Settings (areas, currency, project lists, the charter template, the team pack, accounts);
    - Planning's ⚙ Setup and ⚖ Modifiers (machines, speeds, OEE, card tags, export/import setup);
    - the 🔬 Learned view's *Apply* and *Use it in the plan* buttons;
    - KPI Sources and the ⏱ Production report paths;
    - importing or removing Library notes;
    - Backups.
  - **For other accounts** these are hidden, and the server refuses them too. Their ⚙ Settings shows only their appearance and their account (🔑 Change password).
  - **Using the app stays open to everyone:** tasks, the A3, loading and reading files, pins, marking the report sent, and so on.
- **🌗 Appearance per account:** light, dark or automatic is kept with each account, so it's the same on any PC they sign in on. Set it in ⚙ Settings or with the ⋯ menu's Dark mode switch.
- **Permissions:** within their modules, everyone can see and use everything, as before.
- **Forgotten password:** an admin who's forgotten theirs runs `node scripts/reset-password.js <username> <new password>` in the app folder on the server (without arguments it lists the accounts).
- **Storage:** passwords are kept only as scrypt hashes, and sign-ins as hashed tokens.

**Only on the server itself:** **Stop server** (the button doesn't show elsewhere) and **restoring a backup**, because it replaces everyone's data. **📁 links to files and folders** open File Explorer on the server, so on everyone else's PC the path is copied instead, ready to paste into File Explorer.

**There's no sign-in:** anyone who can reach the address can use it, so keep it on the company network.

## 2a. The planner on its own (on a server)

Planning can run as a separate app, **CI Planner**, on one computer (a server) that everyone opens in their browser. Nobody else needs to install anything.

- **Start it:** double-click **`planner.bat`** on the server. It runs from the same folder and code as the CI Manager (so `update.bat` updates both), but in planner mode:
  - **its own database:** `%LOCALAPPDATA%\CIPlanner\planner.db` (change with `PLANNER_DATA_DIR`), with its own backups;
  - **port 3100**, open to the network (`PLANNER_PORT`, `PLANNER_HOST`);
  - **Planning only:** no projects, tasks, KPIs and so on. Only the Activity log and Backups stay in the ⋯ menu, and other parts of the API answer *Not part of the planner*.
  - Everyone opens `http://SERVERNAME:3100`. Windows may ask to let Node through the firewall the first time.
- **Moving your setup over:** in your own CI Manager, Planning → ⚙ Setup → **⬇ Export setup** (machines, speeds, OEE, Matching machines and speeds, modifiers, shift values, card tags, pins and the planning settings). On the server, use **⬆ Import setup…**. The plan history isn't moved; it builds up again from the exports.
- **Giving a new user your history:** **⬇ Export setup + history** adds the history built up from the exports (each export read and each job seen, which the pace, catch-up and on-time figures come from) and the ⏱ Production runs. **⬆ Import setup…** on the new install replaces the setup as usual but **adds** the history to its own: exports and runs it already has aren't added twice, and for a job both know, the more recent sighting wins. The imported exports are filed under the new install's own export path, so its next read carries straight on. As everyone reads the same exports from then on, their figures stay in step (except for any time a PC is off, when that copy misses the exports).
- **Handing it out on the network:** put the *planning-setup-with-history-….json* file next to `CIManager-Setup.bat` on the share. The installer records that folder (`SHARED_DIR` in `app\.env`, as a `\\server\share` path), and the app applies the newest `planning-setup*.json` there by itself, at start-up and every 30 minutes, once per file: the **history is merged** (never twice), and the **setup is used only on an install that has no planning setup yet**, so nobody's own changes are overwritten. Put a newer export there now and then and everyone's history catches up on its own. Planning › ⚙ Setup shows the file applied and what it added.
- **Team pack (contacts and project lists):** Settings › 📦 Team pack › **⬇ Export team pack** saves the contacts lists (People with their roles, Departments and any lists added) and the project categories and policy deployment lists as `cimanager-team-<date>.json`. Put it next to `CIManager-Setup.bat` with the other files: each install picks up the newest one by itself (at start-up and every 30 minutes, once per file) and **adds** what it doesn't have yet. Nothing is removed or overwritten; a person's role or department is only filled in where it's blank. **⬆ Add from a team pack…** does the same by hand.
- **Your own copy's Planning tab:** Setup → *Shared planner address* (e.g. `http://servername:3100`). The Planning tab in your CI Manager then opens the shared planner.
- **👥 Who's here:** each person gives a name the first time they open the planner. The Planning toolbar shows who else has it open. When someone changes the planning setup after your page was drawn, a yellow note says who and when, with a 🔄 Refresh button, so you don't overwrite each other unawares. The Activity log also records who made each change.
- **🔒 One copy per database:** a lock file beside the database (`planner.db.lock`) records which computer, user and process has it open, refreshed every 20 s. A second copy started on the same database stops, saying who has it and the address to open instead. This guards against two people each starting `planner.bat` against one database in a shared folder, which can corrupt a SQLite file. A lock not refreshed for 90 s (a crash or power cut) is taken over automatically. The same lock protects the CI Manager's own database.
- **Keep the database on the server's own disk,** not a mapped drive. SQLite on a network share is fragile even for one user. With the planner on a server, everyone goes through that one copy, which is safe.
- **No sign-in:** anyone who can reach the server's port can use and change the planner. Keep it on the company network. The shared planner can't be stopped from a browser; close its window on the server.

## 3. Backups & restore

- The Library's notes are in the database, so they're backed up; its images and attachments are in `library\` in your data folder (your Obsidian vault remains their source — import again to restore them).
- Each backup writes a database copy to `backups\db\` and a JSON export to `backups\json\`, inside your data folder (`%LOCALAPPDATA%\CIManager\backups`).
- **Take a backup now:** the **Backups** page, or `npm run backup`.
- **Restore in the app:** on the **💾 Backups** page, click **⤺ Restore** next to any backup, or **⤺ Restore from file…** to pick a `.db` or `.json` backup from anywhere (e.g. a copy on OneDrive or a USB stick). It shows what the backup contains and asks you to confirm; a safety backup of the current data is taken first, so a restore can be undone by restoring that.
- **Restore from the command line:** `npm run restore -- "%LOCALAPPDATA%\CIManager\backups\db\taskmgr-YYYYMMDD-HHMMSS.db"` (a `.json` backup works too). It asks you to confirm, then takes a safety backup of the current data before replacing it. Run `npm run restore` with no file to list the available backups. It's best to stop the app first.
- A backup `.db` file is a normal database, so you can also just open it in DBeaver to look something up without restoring.
- **Tip:** set `BACKUP_DIR` in `.env` to a OneDrive or network folder so the backups are kept off your PC.

## 4. Working with the data directly (DBeaver)

DBeaver offers to download the SQLite driver the first time. You can do this while the app is running.

| `notes` | The additive, time-stamped notes |
| `reminders` | Pending and dismissed reminders |
| `ideas` | Ideation tickets; `ref` (`IDEA-0001`…) is assigned automatically, `project_id` is set when escalated |
| `idea_notes` | Notes on ideas |
| `areas` | The *Area* list for ideas |
| `settings` | App settings (e.g. currency symbol, when the report was last sent) |
| `task_links` | Gantt dependencies: `task_id` waits for `depends_on_id` |
| `project_costs` | Costs logged against a project's budget |
| `project_team`, `project_kpis` | The charter's team members and improvement KPIs |
| `lookups` | The Category and Policy deployment pick-lists |
| `audit_log` | Every change, with old and new values as JSON and when it happened |

**Dates and times** are stored as UTC text in the form `2026-10-31T17:00:00.000Z` (note the trailing `Z`: UTC, not local time). The database rejects anything in another format, so hand edits can't break sorting or the due-date alerts. Due dates (`due_at`) are whole days, stored as the last moment of that day in local time (e.g. `2026-10-31T23:59:59.999Z` in winter in the UK). You don't need to set `updated_at`, `completed_at` or the audit log yourself; the triggers handle them.

**Microsoft Access / Excel (optional):** install the free *SQLite ODBC driver* (by Christian Werner). Then use *External Data → New Data Source → From Other Sources → ODBC* and link the tables for queries and reports. Edits made that way are captured in the audit log too.

## 5. Configuration (`.env`)

| Setting | Default | Meaning |
|---|---|---|
| `PORT` / `HOST` | `3000` / `127.0.0.1` | Where the app listens. Keeping `127.0.0.1` means only your own PC can reach it. |
| `DATA_DIR` | `%LOCALAPPDATA%\CIManager` | Folder for the database, backups and logs. Avoid OneDrive-synced folders for the live database. |
| `DB_FILE` | `DATA_DIR\taskmgr.db` | The database file |
| `BACKUP_DIR` | `DATA_DIR\backups` | Where backups go (a OneDrive or network folder is a good choice) |
| `BACKUP_INTERVAL_HOURS` | `24` | Hours between automatic backups (`0` turns them off) |
| `BACKUP_KEEP` | `30` | Number of backups of each type to keep |
| `LOG_DIR` | `DATA_DIR\logs` | Daily log files |
